# WOM Par 0.1: Sol session and Muse improvement experiment

2026-11-04. Baseline: commit `f616d59`, as recorded in [WOM Par 0.1](../0.1.md).

**Subsequent runtime update:** the owner requested promotion of the conservative candidate into the placement agents. Its guarded form is now active as [`polish-v1`](../0.1.md#updated-runtime-placement-technique). The results and experimental status below describe the initial comparison before that promotion.

The coding-session optimizer change produced a modest, measured placement improvement. Live Muse Spark 1.3 and Muse Wonder 1.0 calls returned concrete proposals, but the depth filters tested from those proposals produced no consistent placement gain. These results concern individual stages, not a validated whole-world WOM Par score. All fitter changes remain experimental; the default fit, planner and placement-agent selection are preserved.

## What was actually tested

- The requested Sol coding session inspected the existing pipeline and implemented candidate local fitting algorithms. No additional OpenAI generation request was needed for this work.
- `MUSE_API_KEY` authenticated real requests to `muse-spark-1.3` and `muse-wonder-1.0` on Meta Model API. Their proposed changes were implemented as separate experimental fitter options and measured on saved assets.
- The comparison imported the frozen fitter directly from Git, then ran it and each candidate on the same photo, mask, depth, camera and asset. No new segmentation, image edits, depth, object generation or Marble generation was purchased.
- The outdoor set contains 23 object/asset pairs: seven floor-supported objects from three photos, using the available IDOL, TripoSplat, Tripo H3.1 and Tripo P1 assets. These are correlated cases, not 23 independent scenes.
- The indoor check used 11 saved IDOL cases from two copies of the same photo. Four cases had identical inputs/results in both worlds. Deduplicating leaves seven distinct object/asset cases, including separately generated head and body assets, from one indoor photo.

The experiment compares specific proposed patches. It does not rank the models' general coding ability: the coding session had interactive repository context and several iterations, while the Muse calls were bounded reviews.

## The useful candidate

`polish` combines two local optimizer changes:

1. When trying a small yaw or pitch change, score it both with the current fitted image position/scale and after snapping back to the bounding box. Keep the lower-loss candidate. Previously, every angle change discarded the refined position and scale by snapping again.
2. Allow up to 32 coordinate-descent rounds instead of 14, keeping the existing early convergence check.

It uses the original 220-pixel fitting raster and original loss. Its explicit options are `refineRounds: 32, preserveTranslation: true` in [fitObject](../../../server/src/geometry/fit.ts). Neither option is enabled by default.

Wins and losses below require an IoU change larger than 0.01; smaller changes count as ties.

| Set / method | Cases | Par 0.1 IoU | Polish IoU | Mean change | Win / tie / loss |
| --- | ---: | ---: | ---: | ---: | --- |
| Outdoor, classic fit | 23 | 0.7559 | 0.7666 | +0.0107 | 12 / 11 / 0 |
| Outdoor, upright grounded fit | 23 | 0.7366 | 0.7430 | +0.0064 | 5 / 17 / 1 |
| Indoor, classic fit, deduplicated | 7 | 0.8225 | 0.8432 | +0.0207 | 3 / 4 / 0 |

Outdoor classic-fit colour error fell from 0.1489 to 0.1445; depth error fell from 0.0284 to 0.0269. Mean absolute ground gap fell from 7.73 to 7.50 cm. That pass took about 11% more fitting time per case (1.09 to 1.22 seconds). These are single-pass local timings: a later one-case check took 1.46 versus 3.40 seconds, so the latency cost needs a dedicated, repeated benchmark.

The indoor colour error fell from 0.1663 to 0.1512, but depth error rose from 0.0151 to 0.0170. The grounded Tripo P1 lemon tree lost 0.0219 IoU. These tradeoffs are why this is a candidate, not an automatic production upgrade.

`fine-polish`, which also raises the fitting raster to 360 pixels, achieved outdoor classic IoU 0.7695, but took about 56% more time and had an outdoor grounded regression of 0.0438. The more conservative `polish` is the stronger next candidate to investigate.

## Muse proposals and measured results

| Source | Proposed change tested | Outdoor classic IoU | Depth error | Finding |
| --- | --- | ---: | ---: | --- |
| Par 0.1 | Original fitter | 0.755863 | 0.028395 | Reference |
| Muse Spark 1.3 | Erode the rendered depth silhouette and reject depth ratios outside 0.9–1.5 | 0.755848 | 0.028876 | Essentially tied IoU; depth and ground gap worsened |
| Muse Wonder 1.0 | Require locally continuous rendered depth, then trim ratios around their median | 0.755152 | 0.027810 | Small depth reduction with a small IoU reduction; no consistent improvement |

Both depth-only filters left the grounded placement unchanged: grounding scales the object about the camera again, cancelling the depth scale change. Indoor IoU changes from these filters were below 0.00005 after deduplication.

Spark also proposed switching the initial depth to the upper quartile when the median is much smaller. That was a no-op on the initial seven IDOL floor cases. Wonder's proposed floor correction overlaps with WOM's existing grounding stage and was not treated as a new improvement.

Earlier session proposals—refining three coarse starts and replacing mask-normalized pixel error with `1 - IoU`—also failed the initial seven-case check. Their mean grounded IoU was 0.7433 and 0.7413, respectively, versus 0.7449 for Par 0.1. They were not promoted.

This includes $0.2121535 for two initial high-effort requests that exhausted their 6,500-token output allowance without a usable answer. The follow-up medium-effort reviews completed and cost $0.1325775. No paid Sol API request was made in this experiment, as requested for the initial session test.

## Deployment and runtime support

`gpt-6.1-sol` is now an opt-in scene director and placement agent (`agent-sol`) in Settings and the viewer. Runtime calls use the server's `OPENAI_API_KEY`; `OPENAI_KEY` remains a fallback alias. Missing OpenAI credentials are rejected before creating/retrying a Sol build or saving a Sol agent selection.

The shared [model adapter](../../../server/src/clients/llm.ts) sends Sol requests through the [OpenAI Responses client](../../../server/src/clients/openai.ts), preserves complete output items and encrypted reasoning between tool turns, and records OpenAI costs under the correct provider. Its optional tool parameters retain their existing semantics. OpenAI conversation storage is disabled for these calls. The default scene planner and agents are still Muse, and the frozen Par 0.1 document is untouched. Nothing was deployed.

This verifies the request protocol locally; live Sol API access and its runtime placement quality have not been tested with this account. The requested first experiment used the coding session itself.

Official compatibility sources: [GPT-6.1 Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol), [Responses migration](https://developers.openai.com/api/docs/guides/migrate-to-responses?api-mode=responses), [Meta model identifiers](https://dev.meta.ai/docs/models).
