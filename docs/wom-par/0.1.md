# WOM Par 0.1

**Updated 2026-11-04: global Par protocol `wom-par-v1` and runtime placement revision `polish-v1`.** This document describes WOM's
generation technique, including the updated runtime placement agents and the "cut head and
assemble" technique used on people. The original comparison baseline remains commit `f616d59`
(tag `wompar-0.1`). This dated amendment incorporates the measured optimizer improvement into
the placement agents; see [Updated runtime placement technique](#updated-runtime-placement-technique).

## Why this document exists

The project defines three related things:

- **WOMetrics** — the evaluation framework: how good is a given 3D world?
- **WOM Par** — a reference reconstruction *system*: how good a world can WOM itself generate,
  measured with WOMetrics? WOM Par is versioned because the underlying models keep improving.
- **WOMgolf** — the competitive layer: others reconstruct the same reference scenes and are scored
  against WOM Par (par = 0; negative beats it).

**WOM Par 0.1 has an original baseline and a dated runtime amendment.** The original models,
prompts and composition code are preserved at `f616d59`, tag `wompar-0.1`. The current checkout
adds the `polish-v1` placement-agent technique and optional GPT-6.1 Sol planning/placement.
Reports must identify which revision they measured. Checking out the original commit reproduces
the original technique, rather than the amended runtime described here.

**WOMPar 0.1 now defines par: 0.** WOMetrics has a representation-independent whole-world
scoring protocol and a **Global** task, alongside its stage diagnostics. The zero anchors exact
frozen reference outputs; it is not a measured claim of perfect quality. Challengers earn a
signed score by playing the same frozen course against those outputs. The initial local
course is a four-photo pilot; no human preference ballots or measured challenger rankings have
been invented from the earlier placement/patrol results.

## The global Par score

For a complete world, show the original photograph and anonymous A/B renders of the candidate
and the frozen WOMPar reference over **the same camera walkthrough**. Ask which better preserves
the photograph as a believable, coherent 3D place to explore. Count a candidate win as 1, a tie
as 0.5 and a loss as 0. Let `p` be the mean preference, averaged by judge, generation trial,
unique source photograph and fixed category weights.

**Par = 100 × (1 − 2p)**, from **−100 to +100; lower is better**.

| Against the frozen reference | Par |
| --- | ---: |
| Candidate always wins | −100 |
| Candidate has 60% preference, including half-ties | −20 |
| Equal preference / exact reference replay | **0** |
| Candidate has 40% preference, including half-ties | +20 |
| Candidate always loses | +100 |

This gives any renderable reconstruction method the same scoring interface: it need not have
WOM's SAM masks, segmented objects, MoGe depth or splat representation. It measures **whole-world
preference on the named course**, not an absolute percentage of geometric truth or a universal
ranking independent of photographs and judges. Unseen regions are judged for plausible
consistency because the photograph cannot establish their real geometry.

### Why this score stays sensible

- **The anchor stays fixed.** Every entrant is compared directly with the same reference.
  Adding a competitor cannot move an existing score. Better future Par releases get separate
  courses; earlier scores are never silently recentered.
- **The evidence stays fixed.** The course hashes its source photos, reference world assets,
  saved layout, camera intrinsics/path, complete captures, capture conditions, rubric and
  judging protocol. Preserve the bytes; regenerating from a model alias and Git tag cannot
  reproduce a stochastic baseline reliably.
- **The world is the unit of judgment.** Source fidelity, completeness, geometry and consistency
  under parallax matter together. A single attractive starting frame cannot hide a collapsed
  novel view. Stage IoU/Intact/contamination, cost and latency remain separate diagnostics.
- **Coverage is mandatory.** Missing scenes, trial outputs, evidence or panel votes leave a method
  unranked. An evidenced generation/render failure loses against success; both failures tie.
  A missing rating is never a tie. More objects, frames or trials cannot inflate a photo's weight.
- **Judges are explicit.** The human track uses at least five distinct, counterbalanced raters
  per photograph/trial. A separate provisional model track freezes at least three judge revisions
  and runs each in both A/B orders. Human and model scores are never pooled or ranked together.
- **Uncertainty is honest.** Report unique photos, full coverage, actual ballots and per-photo
  results. A negative point estimate on a convenience pilot does not establish a general
  improvement. Independent representative courses can additionally report the conservative
  photo-level bound implemented in WOMetrics; frames are not independent samples.

## Pipeline: how a photo becomes a world

| Step | Model / agent | What it does |
| --- | --- | --- |
| Scene plan | **Muse Spark 1.3** (`muse-spark-1.3`, default), Muse Wonder 1.0 (`muse-wonder-1.0`), or optional GPT-6.1 Sol (`gpt-6.1-sol`) | Reads the photo and picks the objects to rebuild separately. For each object: a box, a point inside it, a short description. Also writes the object-removal instruction and the world prompt. Decides, per person, whether to split head/body (see below). |
| Segmentation | **SAM 3.1** (`sam-3.1`, Meta Model API) + Muse Spark review | A box+point prompt and a concept prompt per object. Muse Spark rates both cutouts; the cleaner one wins. |
| Head/body split | **SAM 3.1** | For a person the plan marks, finds face/neck/hands/clothing/arms and replaces the person with an overlapping head and body. Detailed below. |
| Clean plate | **Muse Image** (`muse-image-1.0`) + Muse Spark review | Erases chosen objects and their shadows; Muse Spark checks the edit and asks for another pass if something is left. |
| Depth | **MoGe-3** (`moge3`, default) on AI3D; MoGe-2 (`moge2`) is the alternative | A metric point map of the photo (object placement) and of the clean plate (background relief). |
| Cutouts | SAM masks + Muse Image | Each object cut out by its mask; occluded or frame-cut objects are completed by Muse Image. |
| Objects | **IDOL** (`idol`, default, Gaussian splats, 262k splats, $0.10) on AI3D | Alternatives: TripoSplat (`triposplat`, splats, $0.05), Tripo H3.1 (`tripo-v31`, textured mesh, $0.30), Tripo P1 (`tripo-p1`, textured mesh, $0.50). |
| Surrounding world | **World Labs Marble 1.1** (`worldlabs`, default, ~$1.26) on AI3D; `worldlabs-draft` (~$0.18) is the cheaper alternative; `none` skips it | Generates a Gaussian-splat world from the clean plate and the scene plan's world prompt. |
| Compose | Local (Node) | Calibrates Marble's camera against the photo, fits each object into place, builds the depth relief, writes `scene.json`. Aligns a split person's head and body to the photo's pixels. |
| Placements | Local fitter + **Muse Spark 1.3**, **Muse Wonder 1.0**, and optional **GPT-6.1 Sol** as tool-using agents | Agents use `auto_fit` with the guarded `polish-v1` refinement, inspect scored overlays, and submit a placement. Computes every placement choice the viewer can switch to (below). |

Source: `server/src/pipeline/run.ts` (orchestration), `analyze.ts` (plan), `segment.ts`,
`cleanplate.ts`, `cutouts.ts`, `generate.ts` (MoGe/IDOL/Tripo/Marble), `compose` (via `run.ts`),
`placements.ts`.

### Placement choices

| Method | How the object is placed |
| --- | --- |
| `fitter` (default) | Local CPU rasterizer: silhouette fit to the SAM mask against MoGe depth, then slid along the camera ray to match MoGe's metric depth. |
| `grounded` | The fitter kept upright along gravity, then scaled about the camera so its base pivot rests on the ground plane. |
| `agent-spark` | Muse Spark 1.3 with the updated `polish-v1` tools, then submits a placement. |
| `agent-wonder` | The same with Muse Wonder 1.0. |
| `agent-sol` | The same with GPT-6.1 Sol through OpenAI Responses; optional. |

### Updated runtime placement technique

`polish-v1` is active in the runtime and benchmark agents' shared `auto_fit` tool
([case.ts](../../server/src/bench/case.ts), [llm.ts](../../server/src/bench/llm.ts)).
It incorporates the conservative `polish` candidate from the
[Sol/Muse experiment](experiments/2026-11-04-sol-muse.md):

1. **Keep a reference.** Run the original upright fitter, with its original 14-round limit.
2. **Refine.** Run the same yaw search with up to **32 coordinate-descent rounds** and the
   existing early convergence check. For a yaw or pitch trial, compare preserving the fitted
   image position/scale with snapping back to the bounding box; keep the lower-loss trial.
   This uses the original **220-pixel fitting raster**, original loss and original depth estimator.
3. **Ground and check.** Ground both results as before and score both through the benchmark's
   renderer. Return the one with higher silhouette IoU; keep the original on ties. The same
   comparison applies when an agent requests a restricted yaw range. It protects the tool from
   the grounded regressions observed in the initial experiment.
4. **Inspect and submit.** The agent starts with `auto_fit`, sees its scores and overlay, and
   can use `render_placement` and `measure_depth` to investigate or adjust it. When it submits
   the returned parameters with source `fitter` or `fitter_refined`, reuse the exact scored pose
   instead of reconstructing it from the rounded tool response. A distinct submitted placement
   is still evaluated as the agent's own choice.

The original `fitter` and `grounded` viewer choices remain reference methods. Split head/body
parts remain excluded from independent placement agents so that their alignment is preserved.
Higher-resolution fitting, multiple coarse starts and the unsuccessful Muse depth-filter
proposals are not enabled in the runtime agent.

The prompt includes `polish-v1`, so the content cache distinguishes updated requests from old
agent conversations. Successful results carry `objects[].placements[method].agentRevision` in
`scene.json`. Older or partially updated placements show **update available** in the viewer;
*Run chosen agents* or `POST /api/worlds/<id>/agents` with `{"agents": [...], "run": true}`
updates them explicitly. An unsuccessful update retains the existing placements in the loaded
scene. A fresh compose uses only matching cached answers in cache-only mode; if the revised
agent has no answer there, it can be run from the viewer. Changing the code does not automatically
rebill every saved world.

**Measured evidence before this runtime promotion:** the unguarded conservative candidate improved
classic-fit IoU from **0.7559 to 0.7666** on 23 outdoor object/asset pairs (seven objects, three
photos), and from **0.8225 to 0.8432** on seven distinct indoor cases from one photo. These are
local fitting measurements, not new live-agent or whole-world scores. Unguarded grounded IoU
improved on average from 0.7366 to 0.7430 but regressed on one case; the runtime comparison now
keeps that case's original fit. Depth/colour and unseen viewpoints can still trade off, and an
agent may choose its own final adjustment. See the experiment for the full metrics and limitations.

Validation commands: `npm run test:placement` checks revision handling, split exclusions, an
actual saved IDOL improvement and the known Tripo P1 regression fallback; `npm run test:llm`
checks provider protocols, the revised tool loop and exact-pose reuse. Saved-asset tests skip
with an explicit reason when those local fixtures are unavailable.

## The cut-head-and-assemble technique (splitting people)

A whole-person 3D model gives the face only a few dozen pixels, so WOM instead builds people with
a large face as two aligned objects: a head and a body. Controlled by `splitPeople`
(`server/src/config.ts`, on by default). Code: `server/src/pipeline/split.ts` (plan + split),
`server/src/pipeline/align.ts` (the alignment job), `server/src/geometry/warp.ts`,
`holefill.ts`, `corrector.ts`, `alignJob.ts` / `alignWorker.ts` (the worker thread).

**1. Plan.** The scene-plan prompt (`SPLIT_RULES`, `server/src/pipeline/analyze.ts`) instructs
Muse Spark to set `split_head_body: true` for a person only when **all** of these hold: the head
(hair included) is at least 14% of the image's height or 10% of its width; the face is turned
toward the camera within about 60°, with both eyes or at least one eye clearly visible; the head
and torso are both in the frame. The model also draws a `head_box`. Code double-checks the box
makes sense before trusting it (`analyze.ts`): at least 1% of the image's area, at least 80%
inside the person's own box, and smaller than 90% of it.

**2. Split.** SAM 3.1 concept prompts find the face, neck, hands, clothing and arms, plus the
regions the detail corrector works on later (eyes, eyebrows, lips, nose) — nine requests,
$0.0225. The cut line is **55% of the way from the chin to the bottom of the neck**
(`yCut = chinY + 0.55 * (neckBottom - chinY)`, `split.ts:158`), and the head and body overlap by
**0.8% of the photo's long side** on each side of that line (`band = max(6px, 0.008 * max(W, H))`,
`split.ts:160`). Where a hand covers the jaw, the jaw is painted in from the surrounding skin. If
SAM finds no face in the head box, no neck, the head above 8% of the person's area, the body above
15% of it, or too much of the person left uncovered by either part, the person is kept as one
object and the log records why (`split.ts:223-227`). A failed SAM call retries once.

**3. Cutouts and 3D.** The head (jaw painted in) and the body are each cut from the photo and sent
to IDOL as separate objects, `<id>-head` and `<id>-body`. Neither goes through Muse Image
completion.

**4. Compose alignment**, run in a worker thread after each part's silhouette is fitted
independently:
   - *Warp* — three passes of block matching at different scales, plus snapping outlines and the
     neck seam onto the masks, move each part's Gaussians sideways in the photo's own view (depth
     and pose are left as the fitter found them).
   - *Seam fill* — from 20 cameras around the person, gaps that open between head and body are
     closed with small patches, kept only where the photo's own camera could not have seen that
     gap.
   - *Detail corrector* — over the eyes, brows, lips and nose, a layer of new Gaussians at photo
     resolution plus a least-squares colour fit reproduce the photo in those regions, fading out
     over 10 px around each one.

   Result: `objects/<id>/model-aligned.ply`, hashed against every input it depended on
   (`manifest.objects[].aligned`). First run on the sample photo: 73 s (later ones reuse the
   result unless an input changed, and a failed stage is skipped with a log note; unaligned parts
   fall back to their fitted poses).

**5. Placements.** The head and body keep the fitter's placement only — placing them with any
other method would pull the two parts apart.

**Only Gaussian-splat models (IDOL, TripoSplat) are split**, since alignment moves Gaussians
directly; Tripo mesh objects are not. Worlds built before this feature existed are unaffected (no
head boxes in their stored plan).

### Measured result (one photo: "Beauty Counter Smile")

Against the same woman built as a single object, from `scene.json`:

| At the photo's camera | One object | Split, silhouette fit only | Split, now |
| --- | --- | --- | --- |
| Colour error over her (of 255) | 23.7 | 24.9 | 16.4 |
| Worst of 10 facial/clothing features, off the photo's | 42.6 px | 33.9 px | 0.9 px |
| Median of those features | 27.5 px | 15.4 px | 0.2 px |

Detail corrector, per region at 2× pixel ratio — colour error (of 255) and sharpness (as % of the
photo's): eyes 29.2→2.1, 39%→68%; brows 24.7→1.8, 41%→61%; lips 18.9→1.4, 62%→69%; nose
15.8→1.4, 26%→58%. Outside those regions (>10 px away), no pixel moves by more than 2.4/255.

**What it does not fix:** seen from the side, the split still shows more see-through pixels inside
her outline than one object (11,916 vs. 8,674 over nine views, down from 15,021 before alignment).
Some of that is between hair and shoulders, where the photo's own camera saw the background (a
patch there would change what the photo itself shows); the rest is holes inside the body model.
**This technique has been measured end to end on this one photo only** — treat the numbers as a
single case study, not a statistically validated benchmark.

## Cost per world (original baseline measurement)

A 4-object outdoor photo, default settings, ≈ **$2.60** total: scene plan + SAM + clean plate +
review + one completion $0.06; MoGe-3 ×2 $0.20; IDOL ×4 $0.40; Marble 1.1 $1.26; both placement
agents ≈ $0.68 (≈$0.07/object Spark, ≈$0.10/object Wonder); asset check ≈$0.04. Turning both
placement agents off: ≈$1.92. A person split into head+body adds $0.12 (one more IDOL job + nine
SAM 3.1 requests). Full breakdown and cheaper variants (TripoSplat, Marble draft, no Marble): see
the main [README § Cost per world](../../README.md#cost-per-world).

The amended `auto_fit` performs two local fits and scores them; that increases CPU work but
does not add an API request inside the tool. The current agent prompt/cache revision can require
fresh paid model calls on the first explicit run. The world agent budget remains $3; new
end-to-end cost and latency measurements for `polish-v1` have not yet been established.

## What WOM Par 0.1 does not yet establish

- The global score now has an executable definition and frozen pilot reference, but no human
  challenger evaluation or representative held-out validation has yet been collected. Reference
  **Par 0 is an anchor**, not an absolute quality measurement. The pilot also does not test
  interactive control quality, dynamic worlds or verified geometry of unseen surfaces.
- The visual patrol is a **VLM-reported** score (Muse Spark 1.3, Gemini 3.8 Flash, GPT-6.1 Terra
  judging their own renders), not yet human-verified; judge precision is only as good as the
  observations marked confirmed/false-alarm so far.
- Nothing repairs the Marble world or the depth relief through observe-to-fix yet; only objects
  have suggested fixes.
- The head/body split's own evaluation (above) is one photo, not a benchmark suite.

## Reproducing the original baseline

1. Check out commit `f616d59` (tag `wompar-0.1`).
2. `npm install`, then set `MUSE_API_KEY` and `AI3D_API_KEY` in `.env` (see `.env.example`).
3. Leave `server/src/config.ts`'s `DEFAULT_OPTIONS` untouched: `plannerModel: 'muse-spark-1.3'`,
   `meshModel: 'idol'`, `worldModel: 'worldlabs'`, `depthModel: 'moge3'`, `splitPeople: true`,
   `placementAgents: ['muse-spark-1.3', 'muse-wonder-1.0']`.
4. `npm run dev`, upload a photo. For the split technique specifically, use a photo with at least
   one person whose head meets the 14%/10% size rule above.

## Running the updated runtime

Use the current checkout and the same default model options. New agent placements use
`polish-v1` automatically. Set `OPENAI_API_KEY` in the server environment when selecting Sol;
Muse and AI3D continue to use their existing keys. In an existing world's viewer, run agents

## Versioning

WOM Par is versioned because the pipeline keeps changing. At the owner's request, this file now
includes the dated `polish-v1` runtime amendment and `wom-par-v1` global scoring definition.
The original `f616d59` / `wompar-0.1` baseline
identifier and its measured results remain unchanged. A comparison must record both the Git
revision and the placement-agent revision so that original and amended runs remain distinguishable.
Further agent-technique changes must bump `PLACEMENT_AGENT_REVISION` and document the new
behaviour; a separately named Par release can then be documented and tagged as 0.2, etc.

The global **protocol**, **course digest** and **judging track** are separate identifiers from
the generation code release. Changing reference assets, source photos, weights, paths, capture
conditions, rubric or evaluator definitions changes the course digest. Preserve old manifests
and bytes, and never compare different digests as though they were the same course. Improving
the runtime does not replace the frozen reference or reset everyone else's score.
